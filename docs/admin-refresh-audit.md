# BACKEND-9: аудит админки и варианты обновления

Статус: исследование во время интервью, 2026-09-24. Пользователь подтвердил
объём: обновить все текущие экраны и добавить дашборд со статистикой. Работа
с телефона нужна для всех рабочих действий роли, включая редактирование и
модерацию. Основные пользователи: администраторы, поддержка, менеджеры
маршрутов и контента; в будущем возможны новые роли. Каждая роль работает
только со своими разделами, администратор может менять права через админку.
У роли есть набор прав по умолчанию, а администратор может добавить или
запретить отдельные права конкретному сотруднику. На первом экране нужны и
ключевые показатели, и рабочие очереди; обращения в поддержку обязательны.
Показатель использования памяти доступен только администраторам. Его точное
значение и остальные метрики ещё уточняются.

## Текущая система

FastAPI монтирует SQLAdmin на `/admin`. Страницы рендерятся Jinja и используют
Tabler, Select2, Flatpickr, jQuery, локальный CSS и JavaScript в `layout.html`.
В backend нет сборки frontend. [ADR-008](https://gitlab.com/travel-platform2/tourism-platform/-/blob/main/docs/decisions/ADR-008-ops-admin-sqladmin.md)
закрепляет серверную админку с cookie-сессией отдельно от mobile JWT.

Главная `index.html` содержит только ссылки на пользователей, поддержку и
доступ. `stats.html` уже показывает скачивания APK и долю версий за 7/30/90
дней; `build_report()` в `app_stats/application/queries.py` считает дни по
Москве. Новый интерфейс должен сохранить определения этих показателей,
включая ограничение срока хранения пользовательских строк и правила подсчёта
пользователя на нескольких версиях.

Покрытие существующих экранов:

| Группа | Экраны и действия |
| --- | --- |
| Пользователи | профиль, звание, история эксперта, подписка Travel+, OTP, смена телефона, SMS-доставка |
| Поддержка | тикеты и чат, сообщения, статьи справки и индекс |
| Доступ | операторы, роли, журнал аудита |
| Контент | статьи, блоки, комментарии, жалобы |
| Маршруты и места | маршруты, прохождения и остановки, места, категории, фото |
| Отзывы и достижения | отзывы маршрутов и мест, достижения, ручные действия, выдачи |
| География | страны, регионы, населённые пункты, дорожные события |
| Рекомендации и уведомления | карточки колоды, реакции, уведомления, токены устройств |
| Настройки и медиа | компания, AI-провайдер, SMS/OTP, вложения |
| Антифрод | холды очков, состояние пользователя, нарушения темпа, пороги |
| Аналитика | статистика APK и версий, главная без метрик |

Общие шаблоны SQLAdmin отвечают за списки, формы и карточки сущностей. Поэтому
единая тема должна менять не только 11 локальных шаблонов, но и элементы
SQLAdmin: навигацию, таблицы, пагинацию, фильтры, формы, ошибки и подтверждения.
Изменение CSS нужно проверить на всех группах и в состояниях пустого списка,
длинного текста, узкого экрана и отсутствия права на действие.
Собственный CSS пока не содержит правил `@media`; мобильную пригодность
нельзя считать решённой только за счёт адаптивных классов Tabler. Принимаемое
требование включает не только просмотр, но и полные формы, фильтры, чат,
модерацию, подтверждения действий и сообщения об ошибках на телефоне.

## Возможные подходы

| Подход | Относительный объём | Польза | Основной риск |
| --- | --- | --- | --- |
| Единая тема SQLAdmin/Jinja, графики без React | 1× | Обновляются все экраны, сохраняются маршруты и операции | Компоненты Bklit/Kokonut служат образцами, их React-код не используется напрямую |
| SQLAdmin/Jinja плюс React для аналитики | 2–3× | Богатые графики и фильтры при сохранении CRUD | Два UI-стека, сборка и изоляция CSS, отдельный контракт данных |
| Полная React-админка и admin API | 5× и больше | Свобода менять рабочие процессы | Перенос CRUD, ролей, аудита, CSRF и тестового покрытия |

Оценки относительные, не календарные. При полном обновлении текущих экранов
серверная тема выглядит наиболее экономичным вариантом. Решение принимается
после интервью и проверки требований к визуализации и мобильным действиям.
Требование полного набора действий на телефоне повышает объём во всех вариантах:
нужны мобильные представления списков, удобные формы и проверка каждого
нестандартного действия. React сам по себе эти сценарии не решает.

[Bklit UI](https://bklit.com/docs/installation) и
[Kokonut UI](https://kokonutui.com/docs) опираются на React/shadcn и Tailwind;
их бесплатные репозитории имеют MIT-лицензию, коммерческие Studio/Pro отдельны.
[Motion](https://motion.dev/docs/quick-start) имеет JavaScript API без React;
его применение имеет смысл только для небольших необязательных переходов с
поддержкой reduced motion. Платные наборы не нужны для выбранного объёма.

## Данные для дашборда

Готовый источник есть для APK и версий приложения: `build_report()`. Для
пользователей, маршрутов, очередей модерации, поддержки, AI и антифрода готового
общего отчёта нет; источники и семантика метрик требуют уточнения. Простое
число строк таблицы не равно «активным пользователям», «обработанным жалобам»
или «успешным AI-запросам». До согласования этих определений нельзя публиковать
такие карточки как бизнес-показатели.

Кандидаты для первой версии: скачивания за выбранный период, динамика по дням,
источники скачивания, активные пользователи и доля сборок по уже существующему
отчёту, быстрые ссылки к рабочим очередям. Дополнительные показатели появятся
после определения формул, периода, задержки обновления и прав доступа.

Ролевые рабочие очереди можно опереть на существующие поля и фильтры:

| Раздел | Возможный показатель | Источник и оговорка |
| --- | --- | --- |
| Поддержка | Тикеты, ожидающие ответа | `SupportTicket.last_human_author`, существующий фильтр `AwaitingOperatorReplyFilter`; исключить закрытые тикеты |
| Маршруты | Маршруты на проверке | `Route.publication_status = pending_review`; уточнить, входит ли сюда проверка отзывов о маршрутах |
| Контент | Статьи и комментарии на проверке | `Article.status` и `ArticleComment.status = pending_review`; показывать отдельными числами |
| Модерация | Новые и рассматриваемые жалобы | `ContentReport.status IN (new, in_review)`; определить ответственного раздела при жалобе на маршрут/место/статью |

Эти формулы предварительные: одних статусов недостаточно для согласованного
значения KPI и разграничения междоменных жалоб. У пользователей разных ролей
дашборд не должен раскрывать числа или ссылки недоступных разделов.
В backend и конфигурации развёртывания не найдено готового источника
системных метрик (Prometheus/Grafana/host exporter). Для RAM/диска нужно
отдельно определить, показываем ли ресурсы контейнера или всего сервера, и
как собирать метрики без расширения прав контейнера и утечки инфраструктурных
данных в операторские представления.

## Ограничения при реализации

- Сохранить проверку ролей `ops`/`admin`, CSRF, cookie-сессию и аудит операций.
  Новые FastAPI-маршруты вне вложенного SQLAdmin требуют собственной проверки.
- Сейчас БД допускает только роли `ops` и `admin` (check constraint в
  `admin_role_bindings`), а большинство экранов доступны любому вошедшему
  оператору. Менеджер маршрутов и контент-менеджер не выражены отдельными
  ролями. Для обещанных разграничений потребуется матрица прав с управлением
  из админки, миграция роли и проверка каждого действия на сервере, а не
  только меню. Изменять права должен только администратор; действие нужно
  фиксировать в аудите.
- Роли записываются в cookie при входе, а `authenticate()` перепроверяет
  только активность пользователя. Отзыв роли во время сессии сейчас не
  применяется сразу; новая модель прав должна предусмотреть отзыв доступа.
- Эффективные права сотрудника: права роли плюс индивидуальные разрешения
  минус индивидуальные запреты. Явный запрет должен иметь приоритет над
  разрешением; обновлённые права применяются на следующем запросе, включая
  прямые URL, а не только кэш навигации. Защита от случайной потери последнего
  администратора и от самостоятельного повышения прав обязательна.
- Форма создания оператора автоматически назначает ему роль `admin`; при
  появлении новых ролей такой default выдавал бы лишние права. Создание
  сотрудника должно требовать явного выбора роли с безопасным значением
  по умолчанию. Изменения ролей и матрицы прав должны попадать в аудит.
- Сохранить URL и функции текущих экранов, а также поведение форм и фильтров.
- Не подключать тяжёлые библиотеки ко всем страницам ради одного дашборда;
  измерить размеры ресурсов и число запросов до выбора графиков.
- Уточнить обновление ролей в активной сессии и доступность Redis для лимита
  попыток входа во вложенном приложении. Это вопросы проверки, не подтверждённые
  дефекты.
- Статистику и дашборд сделать читаемыми при пустых данных и на узком экране.
