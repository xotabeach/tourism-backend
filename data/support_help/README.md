# Проверенная по коду справка и поиск инструкций — SUP-01

15 статей для готовящейся сборки `0.2.31`. Статус корпуса — **draft**:
сверка с кодом выполнена, выпуск и редакционное одобрение владельцем
не подтверждены. Корпус не опубликован. Код поискового помощника готов
локально, но до публикации он не предлагает эти статьи через API.

## Единый источник

- `manifest.json`: стабильный ID статьи, revision, прежний FAQ ID,
  категория, название, вопрос, разрешённый Markdown-файл и evidence.
- `articles/`: только пользовательские инструкции. Первый заголовок
  совпадает с manifest; дальше — абзацы и заголовки второго уровня.
- Backend/mobile SHA фиксируют проверенные исходники, не состояние сервера.
- `status=published` требует `release_verified=true` и `approved_by`.
  Эти поля нельзя заполнять только ради прохождения валидации.
- Детальный аудит и нерешённые продуктовые вопросы находятся в локальном
  `tourism-platform/docs/support-faq-audit-2026-09-08.md`, не в RAG-корпусе.

## Проверки

Из корня backend:

```bash
uv run python scripts/check_support_help.py
uv run pytest tests/unit/test_support_help_content.py -q --no-cov
uv run python scripts/check_support_help.py --check-mobile ../tourism-mobile/lib/features/settings/data/support_faq_content.dart
```

`--dart` печатает детерминированный bundled FAQ для применения в mobile.
Файл `support_faq_content.dart` не редактируется вручную: изменять статьи
и manifest, повторять экспорт и проверку совпадения. Команда не пишет файлы,
не подключается к базе или модели и ничего не публикует.
Bundle включён только в соответствующую готовящуюся сборку, без зависимости
от нового API и без сетевой загрузки при открытии FAQ. Старые ID сохранены.
Весь ответ доступен при прокрутке, в том числе пояснения и ограничения.

## Хранение редакций и публикация

Миграция `0056_support_help` создаёт отдельную `support_help_revisions`,
`0057_support_help_embeddings` — изолированный индекс MiniLM.
Перед запуском обновлённого backend владелец применяет миграции.
Туристические `knowledge_chunks`, обращения пользователей и внутренний
`docs/` не участвуют в импорте или поиске справки.

```bash
uv run python scripts/import_support_help.py
```

По умолчанию это только проверка и preview: даже подключения к DB нет.
Запись требует явного `--apply`. Для публикации нужны подтверждение выпуска,
редакционное одобрение в manifest и будущий `--review-until` в ISO-формате
с часовым поясом. Не включать эти поля без фактической проверки владельцем.
Импорт транзакционный; повтор того же содержимого и статуса ничего не меняет.

- ID, revision, точная версия приложения и язык задают уникальную редакцию.
- Текст и метаданные уже импортированной редакции нельзя переписать:
  требуется увеличить revision. История сохраняется.
- Публикация новой редакции отзывает предыдущую опубликованную для той же
  версии/языка. Старая ссылка перестаёт открываться, нет подмены новым текстом.
- `withdrawn` нельзя восстановить, опубликованное нельзя превратить в draft;
  для новой публикации нужна новая редакция.
- Истечение `review_until` скрывает статью. Повторный импорт не продлевает
  проверку автоматически; повторное одобрение оформляется новой редакцией.
- Импорт `status=withdrawn` явно отзывает перечисленные редакции.
  Удаление статьи из manifest само по себе не отзывает её в DB.

## Поисковый API и приложение

- `POST /api/v1/support/help/search`: JSON `q` (до 400 символов) и
  `app_version` (например, `0.2.31`). Свободный вопрос не помещается в URL.
- `GET /api/v1/support/help/{article_id}`: обязательные `revision` и
  `app_version`; полная статья или `404`, если редакция недоступна.
- Открыта только публичная справка: published, `ru`, точная версия,
  наступившая дата публикации и неистёкшая проверка. Ограничения применяются
  до top-k и повторно при чтении. Private ticket API остаётся авторизованным.
- Поиск: русский PostgreSQL FTS, затем при отсутствии результата более
  мягкое совпадение только заголовка/вопроса. Максимум три статьи.
  При включённом semantic-флаге выдача объединяется с MiniLM; `method`
  показывает `full_text` или `hybrid` по реально выполненному поиску.
  Ответ, сгенерированный чат-моделью, не создаётся.
- Выдача различает отсутствие опубликованного корпуса (`available=false`)
  и отсутствие совпадений. Успешные ответы имеют `Cache-Control: no-store`;
  общего кеша вопросов/ответов в этом модуле нет.
- Mobile передаёт реальную версию сборки; при открытии повторно запрашивает
  выбранную редакцию. Отозванный результат не заменяется bundled-текстом.
  Отдельные разделы bundled FAQ по-прежнему доступны без сети.
- «Написать оператору» переносит вопрос в поле существующего чата поддержки.
  Отправка — отдельное действие пользователя. Нет автоматического решения,
  LM-ответа, обещания срока оператора или скрытой передачи переписки.
  «Уточнить вопрос» выделяет текст в поле, не делает новый запрос автоматически.

## MiniLM: включение только после проверки

Используется существующий `SentenceTransformerEmbeddingProvider` и общий
процессный кеш весов RAG. Поддерживается multilingual MiniLM L12 v2,
384 измерения. `hash-v1` и произвольная другая 384-мерная модель не подходят.
Никаких новых вызовов чат-API или передачи вопроса облачной LM нет.
Зависимости — уже существующий extra `rag`; модель должна быть доступна
на хосте. Первый холодный запрос может вернуться к FTS во время загрузки.

Отдельная таблица хранит векторы коротких источников: заголовок/вопрос и
абзацы с темой статьи. Длинные фрагменты делятся по tokenizer-окнам модели
с перекрытием, а не молча обрезаются до первого окна. Окна одной статьи
объединяются по максимальному cosine; одна статья не занимает три карточки.
FTS и semantic объединяются по позициям (RRF), не сложением разных score.

Индекс привязан к UUID редакции, content hash, model ID и `paragraphs-v1`.
Смена весов или правил разбиения требует нового search profile и переиндексации;
одинаковая размерность не означает совместимость моделей. Для небольшого
корпуса используется точное сравнение массивов, без отдельной vector DB:
максимум 500 статей, 64 окна на статью и 2000 окон в выдаче данной версии.

```bash
# Только чтение DB: без загрузки модели или записи индекса
uv run python scripts/index_support_help.py --app-version 0.2.31

# Только после одобрения и фактической публикации статей владельцем
uv run --extra rag python scripts/index_support_help.py --app-version 0.2.31 --apply
```

CLI индексирует только опубликованные неистёкшие редакции, не меняет статус
статей. Повторный запуск идемпотентен. Полностью draft-корпус даёт 0 статей.

Настройки после публикации и проверки на целевом хосте:

- `RAG_EMBEDDING_MODEL=sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`
  (или уже используемый короткий ID той же модели; туристическую модель
  нельзя переключать ради справки без отдельного согласования).
- `SUPPORT_HELP_SEMANTIC_ENABLED=true`; default **false**.
- `SUPPORT_HELP_SEMANTIC_MIN_SCORE=0.55` — экспериментальный порог cosine,
  не вероятность правильности ответа.
- `SUPPORT_HELP_SEMANTIC_TIMEOUT_SECONDS=1.5` — бюджет вызова embedder.

На сервере переменные должны попасть не только в `.env`, но и в окружение
backend-контейнера. Этот срез не меняет удалённый Compose/деплой-скрипт;
передача новых support-переменных через deploy wrapper тоже не автоматизирована.
При старой/отсутствующей модели или индексе, ошибке, таймауте либо занятом
encoder остаётся FTS. В процессе не копится очередь вычислений: один
in-flight запрос, включая работу потока после таймаута. Тексты запросов
не кешируются и не включаются в новые сообщения логов этого модуля.

Публикация, версия, hash, модель и профиль проверяются до semantic top-k,
а разрешённость статьи снова проверяется после вычисления вопроса и при
открытии. Устаревший индекс не может вернуть отозванный источник.

## Проверка второго среза

```bash
REQUIRE_INTEGRATION_DEPS=1 uv run pytest tests/unit/test_support_help_content.py tests/integration/test_support_help_search.py -q --no-cov
```

Нужна локальная PostgreSQL с миграцией `0057`. Тестовые публикации выполняются
для искусственных версий приложения внутри откатываемых транзакций.
`tests/data/support_help_search_eval.json` содержит 40 регрессионных запросов:
28 с ожидаемой статьёй в top-3 и 12 вне справки. Это небольшой подобранный
набор, не независимая оценка качества на реальных обращениях.

Для воспроизводимого локального эксперимента с настоящей моделью:

```bash
RUN_MINILM_EVAL=1 HELP_EVAL_SPLIT=development REQUIRE_INTEGRATION_DEPS=1 HF_HUB_OFFLINE=1 uv run --extra rag --extra dev pytest tests/integration/test_support_help_search.py::test_real_minilm_retrieval_evaluation -q -s --no-cov
RUN_MINILM_EVAL=1 HELP_EVAL_SPLIT=held_out REQUIRE_INTEGRATION_DEPS=1 HF_HUB_OFFLINE=1 uv run --extra rag --extra dev pytest tests/integration/test_support_help_search.py::test_real_minilm_retrieval_evaluation -q -s --no-cov
```

Нужны заранее загруженные веса. Создаются только искусственные тестовые
публикации внутри откатываемой транзакции. В обычном CI этот тест пропускается;
остальные проверки не требуют torch или весов. Настоящий набор —
`tests/data/support_help_semantic_eval.json`: 25 development + 25 контрольных
вопросов, в каждом 15 тематических и 10 вне справки. Это синтетические
формулировки, не обезличенная выборка реальных обращений.

На контрольной части при пороге 0.55: FTS нашёл ожидаемую статью в top-3
для 5/15 вопросов, гибрид — 8/15; посторонние результаты — 3/10 у обоих.
На 40 прежних регрессиях оба способа сохранили 28/28 нужных статей и
0/12 посторонних выдач. Для этого прогона использовать `HELP_EVAL_SPLIT=regression`.
Улучшение ограничено; модуль нельзя считать надёжным решателем проблем.
Гибридная выдача остаётся экспериментальной и по умолчанию выключена.

## Дальше

Сначала редакционное одобрение, проверка выпуска и ручной smoke.
Для улучшения качества нужны проверенные поисковые формулировки тем и
более строгая оценка релевантности мягкого FTS; контрольную выборку после
дальнейшей настройки нужно обновить. Просто снижать cosine-порог нельзя:
в эксперименте это добавляло постороннюю выдачу.
Генерация ответа, assistant runs и журнал фактических действий остаются
отдельным следующим этапом. Отели/кафе не входят в этот срез.
